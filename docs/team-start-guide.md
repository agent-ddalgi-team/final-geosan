## 2-1. 윈도우(PowerShell) 사용자 — 줄바꿈 정리와 검사 명령 (2026-10-22 추가)

맥과 윈도우는 줄바꿈 문자가 달라(LF / CRLF) 같은 파일도 "전체가 바뀐 것"처럼 보일 수 있다. 저장소 루트의 `.gitattributes`가 모든 텍스트 파일을 **항상 LF**로 저장·받도록 정했으므로, 새로 받는 클론은 손댈 것이 없다. **이미 클론을 받아 둔 사람**은 아래를 한 번만 한다(커밋 기록이나 내 작업은 지워지지 않는다. `reset --hard`는 쓰지 않는다).

```powershell
git status                 # 1) 바꾸던 파일이 있으면 먼저 치워 둔다 (없으면 2)로)
git stash                  #    (바꾸던 파일이 있을 때만) 잠시 보관
git switch develop
git pull                   # 2) .gitattributes를 받는다
git read-tree HEAD         # 3) 파일 목록을 다시 읽고
git checkout-index -af     # 4) 내 컴퓨터의 파일을 LF로 다시 써 낸다 (내용은 그대로)
git status                 # 5) 아무것도 안 나오면 정상
git stash pop              #    (1에서 stash 했을 때만) 보관한 변경을 되돌려 놓는다
```

- 3)·4)는 "저장소에 적힌 그대로 파일을 다시 써 내는" 명령이라 커밋된 내용이 바뀌지 않는다. 다만 **바꾸던 파일을 덮어쓰므로 1)의 `git stash`를 먼저 한다.**
- 작업 중인 가지가 있으면 그 가지로 돌아가 `git merge develop`으로 `.gitattributes`를 가져온다.
- 편집기는 `.editorconfig`를 읽어 새 파일도 LF로 저장한다(VS Code는 "EditorConfig for VS Code" 확장을 설치한다).
- Prettier 검사에서 `Delete ␍`가 나오면 그 파일이 CRLF라는 뜻이다. 위 절차를 다시 하거나 편집기 오른쪽 아래 `CRLF`를 눌러 `LF`로 바꾼다.

**한글 깨짐(CP949) 오류가 나면**: 윈도우는 파일을 기본으로 CP949로 읽어 `UnicodeDecodeError … cp949`가 날 수 있다. `.venv\Scripts\python scripts\check.py`는 하위 명령을 자동으로 UTF-8 모드로 돌리므로 그 명령으로 검사한다. `pytest`나 `python -m geosan …`을 직접 부를 때는 PowerShell에서 한 번 `$env:PYTHONUTF8 = "1"`을 하고 부른다(2026-10-22, 이슈 #33).

**심볼릭 링크 권한 오류(`WinError 1314`)가 나면**: 테스트 하나가 심볼릭 링크를 만들어 거부되는지 검사한다. 윈도우 설정 → 개발자용 → **개발자 모드**를 켜면 일반 계정도 링크를 만들 수 있다(이강욱 PC에서 확인, 2026-10-22). 잠금 파일(`requirements.lock`)은 2026-10-22부터 운영체제 조건이 붙어 있어 윈도우에서도 `pip install -r requirements.lock -e .`가 그대로 된다(리눅스·맥 전용 `uvloop`는 자동으로 건너뜀).

**가상환경 켜기**: `.venv\Scripts\Activate.ps1`. "이 시스템에서 스크립트를 실행할 수 없으므로…" 오류가 나면 한 번만 `Set-ExecutionPolicy -Scope CurrentUser RemoteSigned`를 하고 다시 한다. 켜지 않고 쓰려면 매번 `.venv\Scripts\python …`으로 부른다.

**검사 명령**: 맥의 `bash scripts/check.sh`와 같은 단계·같은 순서를 파이썬판으로 돌린다.

```powershell
.venv\Scripts\python scripts\check.py            # 파이썬 + 화면 전부
.venv\Scripts\python scripts\check.py python     # 파이썬만
.venv\Scripts\python scripts\check.py web        # 화면만
```

## 4. 일하는 순서 (팀원)

1. **이슈 번호부터 확인한다.** 내가 할 일의 이슈가 GitHub에 있는지 본다. 없으면 '작업' 양식으로 이슈를 만든다(같은 일의 이슈가 이미 있으면 그것을 쓴다). 가지 이름은 `이름/이슈번호-짧은설명`으로 만든다. 번호가 없거나 닫힌 이슈면 PR을 열 때 `pr-link` 검사가 빨간 X를 내니 처음부터 맞게 만든다. (4-2장)
2. `develop`을 최신으로 받는다: `git switch develop && git pull`. **내 PR이 합쳐진 뒤 다음 일을 시작할 때는 꼭 이걸 먼저 한다.** 작업 중에 받을지는 상황 봐서 정한다. (가지 역할: `develop` = 기본·통합 가지, 모든 PR의 대상. `main` = 시연·전달용, PM만 `develop` → `main` PR로 옮긴다. 2026-10-22 PM 결정)
3. 가지를 딴다: `git switch -c <이름>/<이슈번호>-<짧은설명>` (예: `dongryeol/12-rules-engine`). 가지는 1~2일 안에 합친다.
4. 맡은 파일만 고친다. 약속 파일(`contracts/`, `contract-summary.md`)에 없는 API 경로·응답 필드·운영 명령·테이블·파일 항목은 만들지 말고 PM에게 먼저 묻는다. 개발을 시작하기 전에 자기 모듈의 기능 설계 문서(`aidlc/spaces/default/intents/261019-geosan-sales-agent/construction/u1-skeleton/functional-design/`의 `entities.md`·`rules.md`·`functional-spec.md`)를 읽는다. 규칙 엔진 담당은 `rules.md`가 기준이며 A정밀 손 계산은 이미 확인된 내용이라 다시 하지 않는다.
5. 기능 하나를 끝낼 때마다 커밋한다. 메시지는 쉬운 한국어 한 문장(예: `A정밀 항목 점수 계산 추가: 0.5는 올림`). `fix`, `wip` 같은 한 단어는 쓰지 않는다.
6. **PR을 올리기 전에 테스트 코드를 먼저 쓰고** 테스트와 코드 모양 검사를 돌린다. 통과했을 때만 PR을 연다. 명령은 `README.md` 3장과 `bash scripts/check.sh [python|web]`(윈도우는 `.venv\Scripts\python scripts\check.py [python|web]`, 2-1장). Python은 `pytest`·Ruff, 화면은 Vitest·Prettier·ESLint. 세 트랙이 다 합쳐지기 전에는 시나리오 테스트와 `verify-case`가 실패하는 것이 정상이고, 자기 PR에서는 자기 단위 테스트만 초록이면 된다.
   - **DB 구조를 바꾸는 PR(`migrations/versions/`에 파일을 더한 PR)은 올리기 직전에 `develop`을 다시 받아(`git merge develop`) 끝 버전이 아직 내 파일의 앞(`down_revision`)이 맞는지 확인한다.** 다른 사람이 먼저 올려 끝 버전이 바뀌었으면 내 파일의 `down_revision`을 그 새 끝 버전으로 고치고, 테스트의 최신 버전 기대값도 함께 맞춘다. 같은 시각에 두 사람이 같은 끝 버전에서 파일을 만들면 DB 이력이 두 갈래가 되어 `geosan init-db`가 멈춘다. (2026-11-04 PM 결정, #267·#261)
7. PR을 올린다. `.github/pull_request_template.md`의 항목을 모두 채우고 **본문에 `Closes #이슈번호`를 적고 제목 끝에 `(#이슈번호)`를 붙인다.** 이 둘이 없거나 이슈에 마일스톤이 없으면 검사 `pr-link`가 빨간 X와 댓글로 알려 주니, 본문·제목을 고쳐 저장하면 다시 검사된다(마일스톤은 이슈에서 고르면 PR에 자동으로 복사된다). 담당자가 여러 명인 공동 이슈는 `Closes`에 적지 않고, 내 몫의 하위 이슈를 만들어 그 번호를 적는다(4-2장). 본문은 비전공자가 읽어도 무엇이 되는지 알 수 있게 쓴다. 약속 파일을 바꿨으면 "예"에 표시하고 PM 확인 뒤에 합친다. 이슈에 무엇을 했는지 쉬운 말 요약 댓글을 남긴다.
8. **여기까지가 팀원의 일이다. 합치기(초록색 Merge pull request 버튼)는 PM과 이강욱만 누른다.** 팀원은 자기 PR이든 남의 PR이든 합치지 않고, 검사가 모두 초록이면 PM에게 "PR #번호 확인 부탁"이라고 알린다. PM(또는 이강욱)이 확인한 뒤 **merge commit**으로 `develop`에 합치며(GitHub 설정에서 squash·rebase는 꺼져 있다), `Closes`에 적은 이슈는 PR이 합쳐지면 자동으로 닫힌다. 빨간 X가 하나라도 있으면 합치지 않는다.

## 4-1. 실제 기업 사례 파일 만들기 (10월 말 부분 시연)

## 4-2. 이슈로 일하기

진행 상황의 기준은 **GitHub 이슈 하나**다. `team-allocation.md`는 역할·담당 폴더 지도, `aidlc/` 기록은 설계·승인 기록이고, "어디까지 됐나"는 이슈만 본다. 칸반 보드는 쓰지 않는다(2026-11-04 PM 결정, #271). 전체 진행 상황은 Issues에서 마일스톤 + 우선순위로 걸러 본다(예: `is:open milestone:"11/15 거산 전달" label:P0`).

- **이슈 만들기**: 저장소 Issues → New issue → 양식 3개(작업 / 버그 / 질문·막힘) 중 고른다. 작업 이슈는 할 일·완료 기준·담당 폴더·관련 계획 문서를 채우고 1~2일 크기로 잡는다. 담당자가 초대 전이면 본문에 이름만 적는다.
- **라벨 13개만**: 종류 `작업`·`버그`·`질문`·`막힘` 중 하나 + 영역 `백엔드`·`화면`·`규칙엔진`·`자료`·`PM` 중 하나 + 우선순위 `P0`·`P1`·`P2`·`P3` 중 하나. `자료`는 실제 기업 사례 파일·근거 정리에 붙인다. 새 라벨은 만들지 않는다. 우선순위는 PM이 붙인다: `P0` = 마감 전 반드시, `P1` = 필요하지만 대체 방법 있음, `P2` = 방문 뒤에 해도 됨, `P3` = 여유 있을 때. 내 할 일 순서는 Issues에서 `is:open assignee:@me label:P0`처럼 걸러 보면 된다.
- **마일스톤**: `뼈대(10/28)`, `10월 말 부분 시연`, `11/15 거산 전달` 중 하나를 꼭 붙인다. 없으면 자동 댓글이 달리고, 그 이슈에 연결한 PR은 빨간 X가 난다. PR에는 연결 이슈의 마일스톤이 자동으로 붙으므로 PR에서는 고르지 않는다.
- **같은 일의 이슈를 두 번 만들지 않는다**: 만들기 전에 Issues에서 검색하고, 있으면 그 이슈에 댓글로 이어 간다. 남은 일이 바뀌었으면 본문을 고친다.
- **여러 사람이 나눠 하는 일은 상위 이슈 + 하위 이슈**: 상위 이슈(예: "10/29 방문 준비") 하나에 사람마다 하위 이슈를 만들어 연결한다(이슈 오른쪽 아래 "Sub-issues → Create sub-issue", 또는 AI 도구에 "#136의 하위 이슈로 연결해 줘"). PR은 **내 하위 이슈**를 `Closes` 하고 상위 이슈는 `관련 #`로 적는다. 상위 이슈 본문의 체크 목록이 다 채워지면 준비가 끝난 것이고, 그때 PM이 상위 이슈를 닫는다.
- **보드는 쓰지 않는다**: 이슈가 열려 있으면 진행 중, PR이 `Closes #번호`로 연결돼 있으면 리뷰 중, 닫히면 완료다. 보드 칸을 옮기라는 자동 댓글과 `PROJECT_TOKEN` 설정은 없어졌으니(#271) PR 본문에 "보드 수동 이동 필요"를 적지 않는다.
- **막히면**: 이슈에 `막힘` 라벨을 붙이고 댓글에 "무엇이 막혔는지 / 무엇을 해 봤는지 / 누구의 답이 필요한지"를 쉬운 말로 적는다. 질문·막힘 양식으로 새 이슈를 만들어도 된다. **충돌(conflict)이 났을 때도 같다.** 억지로 풀지 말고 `막힘` 라벨을 붙이고 어느 파일에서 났는지 적어 PM에게 알린다.
- **AI 도구에 시킬 때**: Claude Code·Codex는 `AGENTS.md`의 이슈 규칙을 읽으므로 "이슈 #12 작업 시작해 줘"처럼 이슈 번호를 알려 주면 가지 이름·PR 연결·댓글을 규칙대로 한다.
- **글은 짧게, 어디인지 먼저**: 첫 줄은 결론 한 문장(됐다 / 안 됐다 / 결정 필요), 항목마다 `[어느 화면 › 어느 줄]` + 실제 예문 하나, 댓글 5줄·이슈 10줄 안, 기술 세부는 맨 아래 접는 칸 "기술 메모". 상태 말머리는 ✅ 됨 / ⏳ 진행 중 / ❌ 막힘 / ❓ 결정 필요 네 가지만. 자세한 것과 예시는 `AGENTS.md` "글쓰기 규칙". AI 도구에 시킬 때도 "글쓰기 규칙대로"라고 한 줄 붙인다.
- **쓰지 말 것**: 이슈·PR에 연락처(이메일·전화), 비밀번호·API 키, 거산 내부 자료.

## 5. 하지 말 것

- `docs/input/`(원본 자료)과 `as-is/`(기존 레포 코드)는 고치지 않는다.
- `.claude/CLAUDE.md`, `.codex/`, `.agents/` 안의 파일은 프레임워크가 관리한다. 손으로 고치지 않는다. 규칙을 바꾸려면 `AGENTS.md`를 고쳐 PR로 올린다.
- 담당자 이름·이메일·전화 같은 개인정보를 저장하지 않는다.
- API 키·비밀번호를 코드에 적지 않는다. 환경 변수로 넘긴다.
- 가상 데이터(A정밀·아연도금 사례 등)는 화면과 출력물에 "가상·거산 실제 사양 아님"으로 표시한다.

## 7. PM: 오늘 이슈 현황 요약 보기

PM이 Claude Code나 Codex에 **"오늘 이슈 현황 요약해 줘"** 라고 하면 AI 도구가 다음을 한다(`AGENTS.md` GitHub 이슈 규칙).

1. 이슈를 읽는다:
   ```
   gh issue list --state all --limit 200 --json number,title,state,labels,milestone,assignees
   ```
2. 마일스톤별로 세 묶음으로 나눈다: **완료**(닫힌 이슈), **진행 중**(열린 이슈 중 `막힘` 라벨 없음), **막힘**(열린 이슈 중 `막힘` 라벨 있음).
3. 쉬운 말 표로 보여 준다. 모양은 아래와 같다.

| 마일스톤 | 완료 | 진행 중 | 막힘 |
|---|---|---|---|
| 뼈대(10/28) | 3건 (#2 기본 틀 1, …) | 5건 (#6 규칙 엔진 구현 – 유동렬, …) | 1건 (#9 평가 흐름 – 이강욱: 규칙 엔진 PR 대기) |
| 10월 말 부분 시연 | 0건 | 4건 | 0건 |
| 11/15 거산 전달 | 0건 | 1건 | 0건 |

4. 막힘 건은 이슈 댓글의 마지막 상황을 한 줄로 붙인다. 마감이 지난 마일스톤이 있으면 표 아래에 한 줄로 알린다.

직접 보려면 저장소 **Issues**에서 `is:open milestone:"11/15 거산 전달" label:P0`처럼 마일스톤 + 우선순위로 걸러 보면 된다(칸반 보드는 쓰지 않는다, #271). 권한은 저장소 **Write** 이상이어야 가지를 올리고 이슈를 고칠 수 있다. 권한을 주는 방법(저장소 admin만 가능): 저장소 Settings → Collaborators and teams → 사람을 고르고 Role을 Write로. 팀원이 Write 권한을 받으면 이슈의 담당자(Assignees)로 지정할 수 있다.
