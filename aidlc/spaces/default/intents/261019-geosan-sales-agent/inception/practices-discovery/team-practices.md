# 팀 실천 방식 초안 (Team Practices) — 거산케미칼 AI 영업지원 에이전트 2차

이 문서는 "우리 팀은 어떻게 일하는가"를 다섯 항목으로 적은 **초안**입니다. 새 프로젝트(그린필드)라서 아직 팀이 확정한 방식이 없으므로, 조직 기본값(`aidlc/spaces/default/memory/org.md`)을 이 팀의 조건에 맞게 고쳐 **제안**으로 적었습니다. 이 팀의 조건은 제약 목록(`../../ideation/feasibility/constraint-register.md`)과 범위 문서(`../../ideation/scope-definition/scope-document.md`)에서 가져왔습니다.

- 4인 전원 비전공자, AI 코딩 도구에 의존 (CON-16)
- 기술은 Python, FastAPI + React, SQLAlchemy, 개발 DB SQLite (CON-01); 구조는 최대한 단순하게 (CON-02)
- 예산 800만 원, 12/11 이후 비용 부담 가정 없음 (CON-14, CON-15); AWS 계정 없음, 실행 환경 미확정 (CON-22)
- 일정: 10/30 초기 동작 → 11/6 첫 흐름 → 11/15 P0+P1 → 11/27 P2 (범위 문서 4절)

각 항목의 마지막 줄 `제안 상태: 인터뷰에서 확정 전`은 아직 팀이 답하지 않은 초안이라는 뜻입니다. 인터뷰에서 확정되면 이 줄은 빠지고, 확정 내용이 `memory/team.md`로 옮겨집니다.

## Way of Working

우리는 **트렁크 기반 개발**(가지를 길게 두지 않고 모두 `main` 한 줄기로 자주 합치는 방식)을 기본으로 합니다. 모든 작업은 `main`에서 가지(브랜치)를 따서 시작하고, 1~2일 안에 다시 `main`으로 합칩니다. 오래 사는 가지는 합칠 때 충돌이 커지므로 두지 않습니다.

- 구현(Construction) 단계의 작업 공간(worktree)은 `main`에서 따고, 합치는 대상도 `main`입니다.
- 한 묶음의 작업(Bolt)을 합칠 때는 **스쿼시 머지**(여러 중간 저장을 하나의 기록으로 합쳐서 넣는 방식)를 씁니다. 묶음 하나가 `main`에 기록 하나로 남아 전달 계획의 묶음 순서와 1:1로 맞습니다. 중간 기록은 감사 로그가 보존합니다.
- 이 팀에 맞춘 이유: 4명이 같은 저장소에서 AI 도구로 빠르게 고치는 환경에서는 가지를 짧게 가져갈수록 "내 코드와 네 코드가 안 맞는" 문제가 줄어듭니다. 기존 팀 레포 방식과 병행(CON-18)하더라도 이 저장소 안에서는 한 줄기 원칙을 지킵니다.
- 다른 환경(시연용·거산 접속용)이 생겨도 가지를 따로 두지 않고, 태그나 환경별 설정으로 구분합니다.

## Walking Skeleton

우리는 **얇은 끝단 조각(워킹 스켈레톤)을 먼저** 만듭니다. 가상 사례 1건(A정밀)이 입력 → 필수조건 필터 → 점수 → 분류 → 추천 목록·근거 상세 화면 → 담당자 의견 저장까지 한 번에 이어지는 최소 동작을 첫 단위(Unit)로 삼고, 그다음 의존 순서대로 살을 붙입니다. 이는 범위 정의 Q6에서 이미 "뼈대 먼저"로 고른 순서이고, 10/30 초기 동작의 정의(P0-6)와 같습니다.

- 활성 범위 `mvp`는 `skeleton: on`이므로 이 의식이 적용됩니다. 첫 단위는 다른 단위보다 먼저 코드 생성까지 끝까지 통과시킵니다.
- 뼈대가 "정말 동작한다"는 확인은 사람이 승인한 **구현 검증 명령**(예: 백엔드 테스트 + A정밀 사례가 기대값 E 77 / P 95 / S 81.1 / R 82로 나오는지 확인)으로 합니다. 설계 검토만으로는 뼈대 완료로 보지 않습니다.
- 뼈대 승인 후, 이후 단위를 자동으로 이어갈지(autonomous) 매 체크포인트마다 검토할지(gated) 한 번 묻습니다. 비전공 4인 팀이고 거산 시연이 잦으므로, 초안 제안은 **매 체크포인트 검토(gated)** 입니다.

## Testing Posture

우리는 테스트를 모든 작업 묶음의 필수 산출물로 봅니다. 다만 전원 비전공자이고 10/30까지 시간이 짧으므로, 테스트를 먼저 쓰는 방식(TDD)보다 "먼저 동작하게 만들고, 바로 그 층의 테스트를 쓰고 돌린다"는 **test-after**를 제안합니다.

- **Methodology**: test-after
- **Methodology evidence**: 조직 기본값(`org.md` Testing Posture, 미확정 시 test-after)과 팀 조건(CON-16 전원 비전공자·AI 도구 의존, CON-17 10/30 초기 동작까지 약 2주)에 근거한 제안. 팀이 TDD/BDD 경험을 밝히면 바꿀 수 있음. 인터뷰 확정 전.
- **Ordering**: 테스트 가능한 각 층(규칙 계산 → API → 화면)을 먼저 구현한 뒤, 같은 작업 묶음 안에서 그 층의 테스트를 작성하고 실행하여 통과시킨다.
- 커버리지: `mvp` 범위의 조직 기본 하한인 **줄 커버리지 80%** 를 유지합니다. 특히 부록 F 점수·11개 분류 분기 같은 규칙 계산은 기획서 시나리오(S01~S14)와 A정밀 계산값(E 77 / P 95 / S 81.1 / R 82)을 그대로 기대값으로 쓰는 테스트를 둡니다. 하한은 통과를 위해 낮추지 않습니다.
- 도구: Python 쪽은 `pytest`(+ `pytest-cov`), React 쪽은 Vitest + React Testing Library 같은 표준 러너를 제안합니다(상세 화면 설계·코드 생성 단계에서 확정).
- 실행 시점: `main`에 합치기 전에 CI(자동 검사)에서 테스트를 돌리고, 실패하면 합치지 않습니다.
- 범위 메모: 외부 LLM 호출(P0-4)과 외부 API(CON-04)는 테스트에서 가짜 응답(mock)으로 대체해 비용과 변동을 없앱니다. 활성 `Test Strategy`는 Standard이며 이 메모는 그 위에 더해질 뿐 줄이지 않습니다.

## Deployment

우리는 **`main`에 합쳐지면 시연 환경에 자동으로 올리고(deploy on merge), 거산이 실제로 쓰는 환경에는 사람이 따로 승인한 뒤 올리는** 두 단계를 제안합니다. 조직 기본값(스테이징 자동, 프로덕션 수동 승인)을 이 팀 조건에 맞게 줄인 것입니다.

- 시연 환경: 10/30, 11/6 이정표에서 팀 노트북 또는 저비용 호스팅 중 하나. 배포 대상·방식 자체는 G0(10/27 목표)와 인프라 설계 단계에서 정하며, 여기서는 "합치면 자동으로 올라간다"는 원칙만 둡니다(CON-22, 범위 문서 P1-6).
- 거산 실사용 환경(11/15 이후): 승인자는 팀 PM + 거산 담당자 확인을 제안합니다. 재접촉 실제 이력은 거산이 지정한 환경에 둔다는 원칙(CON-13)을 배포 설계에서 지킵니다.
- 되돌리기: 어떤 배포든 직전 버전으로 되돌리는 절차를 문서로 둡니다. SQLite 개발 DB를 쓰는 동안은 배포 전 DB 파일 백업을 되돌리기 수단으로 삼습니다.
- 비용: AWS 계정이 없고(CON-22) 12/11 이후 비용을 팀이 계속 부담하지 않으므로(CON-15), 무료 또는 월 수천 원 수준에서 멈출 수 있는 방식을 우선 검토합니다. 구체 서비스명은 인프라 설계에서 비교합니다.

## Code Style

우리는 저장소에 둔 설정 파일이 정한 규칙을 따르고, 사람이 손으로 고치지 않고 도구가 자동으로 맞추게 합니다. 전원 비전공자이므로 "규칙을 외우는 것"이 아니라 "저장하면 도구가 고쳐 주는 것"을 기본으로 합니다.

- Python: 포매터·린터 모두 **Ruff** 하나로 통일하는 안을 제안합니다(설정은 `pyproject.toml`). 조직 기본값은 Black + Ruff이지만, 도구가 하나면 비전공 팀이 익히기 쉽습니다. 이름은 `snake_case`.
- JS/TS(React): 포매터 **Prettier**, 린터 **ESLint**(설정은 저장소 루트 `.prettierrc`, `eslint.config.*`). 이름은 `camelCase`, 컴포넌트는 `PascalCase`.
- CI에서 포매터·린터를 먼저 돌리고, 오류가 있으면 합치지 않습니다.
- 가상 데이터 표시: 화면과 출력물에서 가상(실제 거산 사양 아님) 데이터는 눈에 띄게 표시하는 공통 부품을 둡니다(CON-10). 이는 스타일이 아니라 규칙이므로 `discovered-rules.md`에도 적었습니다.
- 그 밖의 이름 규칙은 린터 설정이 다루지 않는 경우에만 코드 생성 단계에서 제안합니다.
