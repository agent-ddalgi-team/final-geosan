# 도메인 설계 질문 (Domain Design)

이 단계는 "코드로 만들 논리 부품(component)"을 나누고, 데이터(엔티티)마다 주인 부품 하나를 정합니다. 배포 모양(한 덩어리인지 여러 서비스인지)은 다음 단계(작업 단위 나누기)에서, 기술 선택(FastAPI·React·SQLite)은 이미 제약(CON-01)으로 정해져 있어 여기서 다시 묻지 않습니다. 요구사항(`../requirements-analysis/requirements.md`)과 사용자 스토리(`../user-stories/stories.md`)에서 확정된 범위·우선순위·규칙 수치도 다시 묻지 않습니다. 여기서는 부품 경계와 데이터 주인에 관해 범위·데이터·보안에 영향이 있는 네 가지만 묻습니다. 세부(부품 이름, 화면 부품 구조, 수집기 어댑터 묶음)는 추천안으로 정하고 기록만 남깁니다.

## Q2. 규칙 엔진을 "저장소를 모르는 순수 계산 부품"으로 분리합니까?

A. 규칙 엔진은 입력 스냅샷(기회·요구·근거·거산 값·규칙 설정)을 받아 결과(항목 판정·점수·분류·순위)만 돌려주는 순수 계산 부품으로 두고, 평가 묶음·평가 기록(EVALUATION_BATCH / EVALUATION_RUN / ITEM_JUDGMENT / REQUIREMENT_CHECK)의 저장과 스냅샷 만들기는 별도 부품(평가 기록)이 맡는다 (추천 — DB 없이 기대값 테스트가 가능하고, 규칙 설정 파일 교체·재현성 확인이 쉬움)
B. 규칙 엔진이 DB에서 직접 읽고 평가 기록까지 저장한다(부품 하나, 코드 양은 적지만 테스트에 DB가 필요)

## Q3. 확인 질문·질문 목록·조사 기록을 별도 부품으로 둡니까?

확인 질문 생성(FR11.1, P0)은 평가 결과에서 나오지만, 질문 목록의 상태(대기/요청/회신/반영)·거산 확인 요청·복사/내보내기(FR11.2, P1)와 추가조사 기록(FR12, P2)은 거산과의 소통 흐름이며 평가 계산과 바뀌는 속도가 다릅니다.

A. "확인·조사 창구" 부품을 따로 두어 확인 질문·질문 상태·요청자/기한·회신 기록·조사 기록(RESEARCH_TASK)을 소유하고, 평가 기록 부품은 "이 평가에서 생긴 질문 후보"만 넘긴다 (추천 — 거산 확인 병목을 푸는 기능이라 지연 시 마지막까지 남기기로 했고, 평가 계산과 독립적으로 바뀜)
B. 확인 질문과 조사 기록을 평가 기록 부품 안에 둔다(부품 수는 줄지만 질문 상태 변경이 평가 기록 코드를 건드림)
