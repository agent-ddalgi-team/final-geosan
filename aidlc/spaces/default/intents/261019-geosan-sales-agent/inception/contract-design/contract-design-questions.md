# 계약 설계 질문 (Contract Design)

이 단계는 단위(`../units-generation/unit-of-work.md`)들이 서로 주고받는 "약속"(계약)을 정합니다. 어떤 데이터가 어떤 모양으로 어떤 방식으로 경계를 건너고, 잘못됐을 때 무엇이 일어나는지입니다. 이 시스템은 한 덩어리(FastAPI + React + SQLite)라 외부에 공개하는 API는 없고, 경계는 네 종류입니다: ① 화면(React) ↔ 웹 API(FastAPI) HTTP 경계, ② 부품 사이 내부 함수 경계(흐름 부품·규칙 엔진·전송 보호·수집 어댑터), ③ 같은 SQLite를 나눠 쓰는 공유 데이터 경계, ④ 사람이 넣는 파일·명령 경계(가상 사례·거산 역량 투입 파일, 규칙 설정 파일, 운영 명령). 이미 정해진 것(한 덩어리 배포, 부품 경계와 교차 참조 규칙 ADR-011, 전송 보호 입력 계약, 쉬운 말 오류, 타임아웃 목록 10초·근거 60초)은 다시 묻지 않습니다. 데이터·보안·운영 부담에 영향 있는 네 가지만 묻습니다.

## Q1. 화면 ↔ 웹 API 경계의 형식은 무엇으로 합니까?

A. JSON REST: 경로 접두어 `/api/v1/…`, FastAPI가 OpenAPI 문서를 자동 생성해 계약서로 삼고, 응답은 항상 `{ data, meta }`(meta에 갱신 시각·가상 데이터 포함 여부·거산 값 묶음) 또는 `{ error }`(쉬운 말 메시지·다음 행동·오류 식별자는 로그 대조용) 형식 (추천 — 비전공 팀이 브라우저에서 문서를 바로 보고 시험할 수 있고 React에서 쓰기 쉬움)
B. GraphQL — 화면이 필요한 것만 골라 받지만 비전공 팀이 익힐 것이 많음
C. 화면이 서버가 그린 HTML을 받음(템플릿) — React·Ant Design 결정과 어긋남

## Q2. 계약의 주인과 바꾸는 규칙은 어떻게 합니까?

A. 제공하는 쪽이 주인: HTTP API는 WebApi(U1이 처음 만들고 뒤 단위가 경로 묶음별로 추가), 내부 함수 계약은 해당 부품(흐름 부품·규칙 엔진·전송 보호·수집 어댑터), 공유 데이터는 테이블 접두사로 소유 부품을 표시. 추가 변경(필드·경로·명령 추가)은 자유이되 받는 쪽은 모르는 필드를 무시하고, 깨는 변경(필드 삭제·의미 변경·형식 변경)은 `/api/v2`처럼 버전을 올리거나 규칙 설정 버전을 올리고 PM 확인 뒤 한 번에 바꾼다 (추천 — 동시 진행 2개 단위가 서로 깨지 않게 함)
B. 버전 없이 수정하고 합칠 때 맞춤 — 동시 진행 중 충돌 위험
X. Other (please specify)

## Q3. 경계에서 잘못됐을 때(오류·타임아웃·재시도) 규칙을 확인합니다.

A. 오류 응답 형식 하나로 통일(위 Q1의 `{ error }`), 오류 코드는 화면에 보이지 않고 로그 대조용 식별자만. 타임아웃: 목록·상세 10초, 평가 1건 1초 목표, 외부 LLM·홈페이지 60초, 외부 소스 API 30초. 재시도: 외부 호출(LLM·HTTP·소스 API)만 1회, 부작용 없는 읽기만, DB 저장은 재시도하지 않고 흐름 전체를 되돌림(ADR-009). 동시 수정은 마지막 저장이 이기되 이전 값 알림(FR7.6) (추천 — 요구사항 NFR2·NFR7·NFR10을 그대로 계약으로)

## Q4. 사람이 넣는 파일(가상 사례·거산 역량 투입, 규칙 설정)의 형식은 무엇으로 합니까?

A. JSON 묶음 파일: 가상 사례 1건 = JSON 파일 하나(고객·기회·요구·신호·이력·근거·거산 값·검수 상태·조사 요건·담당자 체크·기대 결과를 한 파일에), 거산 역량 = JSON 파일 하나, 규칙 설정 = YAML 파일 하나(버전·해시 기록). 산단공 등 외부 원본만 CSV 그대로. 투입 명령이 형식 검사 뒤 어떤 항목이 틀렸는지 알림 (추천 — 한 파일이 한 사례라 PM이 확인·수정하기 쉽고 기대값과 입력이 같이 있음)
