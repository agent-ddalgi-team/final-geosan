## 1. 산단공 API 확인 결과 (2026-11-05 공공데이터포털 상세 페이지 기준)

- 응답은 회사명·주소·업종·생산품·공장관리번호(기본 정보 + 업종 + 생산품). 세부 열 이름은 활용신청 뒤 명세서에서 확인.
- 비용 무료, 이용허락 제한 없음, 개발계정 하루 1,000회. 외부 사용 기록(한 개발 저장소)에 따르면 JSON을 요청해도 XML로 오는 경우가 있고 100건×5쪽까지만 읽혔다 → **활용신청 뒤 시험 2개**: (a) 단지 하나를 끝까지 넘길 수 있는지, (b) 응답 형식.
- 산단공 전국등록공장현황 CSV(15105482): "월 마지막 일 기준으로 출력", 포털 수정일 2026-09-23, 열 5개(회사명·단지명·생산품·공장주소). 로그인 없이 스크립트로 내려받을 수 있는지는 **미확인**(브라우저로 받는 것만 확인됨). 그래서 CSV는 자동이 아니라 예비다.
- 충청남도 천안시_공장(제조업체)현황 CSV(15005040): 시도·시군구·회사명·공장구분·전화번호·생산품·업종명·주소. 연간 갱신. **지자체 자료라 약속의 자동 소스 3개(CON-04) 밖**이고 전화번호 열이 있다. 쓰려면 PM이 소스 4번째로 넓히는 결정을 먼저 해야 한다. 이 제안서는 넣지 않는다.

**한계 한 줄**: 산업단지 밖에 있는 공장(개별입지)은 API 산업단지명 조회로 못 잡는다. 충남 소규모 가공 업체 중 이런 곳이 많다. 그래서 CSV(전수)를 예비로 남기고, 몇 달 돌려 본 뒤 개별입지 보강 방법(지자체 CSV 또는 회사명 조회 보조)을 다시 정한다.

## 2. 후보 자동 수집 설계 (#221 방향 변경)

**🎯 바뀌는 것** — 지금 #221은 "PM이 CSV를 받아 명령으로 넣음"이다. 끝나면 서버가 매달 스스로 산단공 API를 불러 새 회사를 목록에 더하고 자동 조사까지 잇는다. 추천 목록 머리에 "11/20 정기 수집 · 새 후보 7곳 · 조사 5/7".

**🔁 흐름** — 매달 1회(설정) → 설정에 적은 산업단지 이름마다 API 조회(쪽 넘김) → 생산품 키워드·지역 거르기(설정 `ingestion.regions`·`productKeywords` 그대로) → 기존 회사와 병합(같은 이름+주소는 건너뜀, 비슷하면 "확인 필요") → 새 회사 삽입(회차 `requestedBy: SCHEDULER`) → 규칙 평가 → 새 회사만 자동 조사 ②→③→④→재평가(C7 `autoResearch`) → 4장 ③ 정기 재조사.

**실행 방식(추천)** — 서버 안에서 하루 한 번 "마지막 정기 회차가 `intervalDays`보다 오래됐나"를 보고, 오래됐으면 같은 `run_ingest`를 뒤에서 돌린다. 동시 1개(기존 409 `INGEST_RUNNING` 규칙 재사용), 실패하면 회차 FAILED로 남기고 다음 날 다시. 별도 서버·크론 없음.
- 🚫 안 고른 방법: Railway에 크론 서비스 하나 더 → 설정·로그가 두 곳으로 늘고 비전공 팀이 볼 곳이 둘이 됨. 서버 안 확인이 더 단순.
- 단지 목록은 PM이 설정에 적는다(처음 천안·아산 10~20개, 출처 산단공 전국산업단지현황통계 파일). 단지 20개 × 2~3쪽 = 월 60회 안팎 → 하루 1,000회 상한 안.
- CSV는 `geosan ingest kicox-factory-csv --file 경로`로 그대로 둔다(예비, 개별입지 보강, PM이 분기 1회).
- 대표번호: API·CSV에서 회사 대표번호가 오면 1차 규칙대로 `mainPhoneSource: CSV`로 채운다(AGENTS.md 2026-11-03 결정). 사람 이름이 붙은 번호·대표자명은 저장하지 않는다.

## 3. AI 점수 입력 제안 — 새 회사가 자동으로 순위에 들어가게

**문제** — 지금 점수 입력값(8항목)·공정 연결(어느 거산 공정에 맞는지)은 사례 파일에서만 채운다. API·CSV로 들어온 회사는 AI가 근거를 뽑아도 점수 입력이 없어 `scoreState NONE`이고 순위에 못 든다. 18곳은 사람이 일일이 적었던 자리다.

**제안** — 근거 추출(C9 `extract_evidence`) 출력에 두 가지를 더한다.
- `itemInputProposals`: 점수 항목마다 `{ itemCode, matchRateProposed, certaintyProposed, factJudged, quote, evidenceRef }`. 근거 없는 항목은 내지 않는다.
- `processLinkProposals`: `{ processCode, basis, quote, evidenceRef }` 최대 3개(설정 공정 목록 안 값만).
- 저장은 출처 `AI`, 상태 `PENDING`. **평가는 AI 제안을 입력으로 바로 쓴다** → 카드·상세 점수는 `scoreState PENDING`(흐리게 + 꼬리표 "AI 제안 · 확인 전", 2026-11-04 결정 #212 ①과 같은 표시). 담당자가 상세 검토사항 줄에서 [확정]/[고치기]하면 출처 `STAFF`·`CONFIRMED`로 바뀌고 재평가.
- 사례 파일 값(`CASE_FILE`)이 있는 항목은 AI 제안이 덮지 않는다(사람이 적은 값 우선). 거래 관계·내부 이력은 제안 대상이 아니다(C4·CON-09 그대로).
- 🚫 안 고른 방법: AI 제안은 저장만 하고 담당자가 확정한 뒤에만 점수에 쓰기 → 새 회사가 "점수 없음"으로 남아 "목록이 자동으로 나온다"는 목표에 못 미침. 흐리게 표시가 이미 있으니 그 규칙을 쓴다.

## 4. 근거 갱신 규칙 ①②③ (PM 지시 2026-11-05)

설정 `research` 칸을 넓힌다. 숫자는 5곳 시험 비용(#219 댓글의 1곳당 호출 수·비용)을 보고 PM이 정한다.

```yaml
research:
  staleAfterDays: 90        # (있음) N일. 5곳 시험 뒤 PM이 정함
  refreshOnOpen: true       # ① 상세를 열 때 N일 넘었으면 자동으로 다시 조사
  periodic:
    enabled: true           # ③ 정기 재조사
    intervalDays: 30        # 2장 정기 수집과 같은 주기(5곳 시험 뒤 정함)
    topN: 30                # 현재 순위 상위 N곳만
    includeNew: true        # 이번 회차 새 후보 포함
```

| 규칙 | 어디서 | 동작 | 약속 변경 |
|---|---|---|---|
| ① 상세 열 때 | 상세 화면 | 상세 읽기(GET)는 읽기만 한다. 응답 `research: { status: FRESH\|STALE\|RUNNING\|LIMIT, researchedAt, staleAfterDays }`. 화면이 `STALE`이면 기존 `POST /homepage`(확정된 주소 그대로, `trigger: AUTO_STALE`)를 자동으로 부르고 머리에 "근거 n일 전 · 다시 조사 중" 띠. 같은 회사 하루 1회, 조사 중이면 409 재사용, 상한이면 띠만("이번 달 한도") | C1 상세 `research` 객체, `POST /homepage` 본문 `trigger` |
| ② [다시 조사] | 상세 머리 | **이미 있음(1차)**. 변경 없음 | 없음 |
| ③ 정기 | 서버 안 월 작업 | 2장 수집이 끝난 뒤, 현재 순위 상위 `topN` + 이번 회차 새 후보 중 `researchedAt`이 N일 넘은 회사만 ②→③→④→재평가를 1곳씩. 월 비용·호출 상한에 걸리면 멈추고 남은 건수를 회차에 기록, 다음 달 이어서 | C7 `research.periodic`, C6 `opp_ingest_batch.researchPlannedCount` |

- 비용 어림: 1곳 4~6센트(`llm-settings-proposal-20261103.md` 어림) × (상위 30 + 새 20) = 월 $2~3. 월 $20 상한 안. 실측값으로 N·주기·topN을 정한다.
- 1차 약속의 "주기 자동 조사는 두지 않고 담당자가 누를 때만"(C1 `POST /homepage` 설명)은 2차에서 "정기 조사(③)는 설정으로 켠다"로 **보강**한다. 1차 코드는 그대로 돌아간다(더하는 변경).

## 5. #224 조사 에이전트 — MCP 연결 검토 항목 (2차 설계 때)

MCP는 "AI 모델이 바깥 도구를 부르는 공통 규격"이다. 2차 설계 때 아래 비교표로 정한다. 지금 결정하지 않는다.

| 비교 | A. 자체 루프(OpenAI 도구 호출, 도구 3개는 우리 코드 안) | B. 우리 도구를 MCP 서버로 열어 모델이 부르게 |
|---|---|---|
| 전송 보호(C4) | 호출 전 검사를 우리 코드가 그대로 쥠 | 모델이 부르는 순간마다 검사해야 하고, 서버를 바깥(OpenAI)에서 부를 수 있게 열어야 함 |
| 노출·인증 | 없음 | Railway 서버에 공개 주소·인증 추가 필요 |
| 비용·걸음 상한 | 최대 6걸음·1곳당 상한을 코드로 | 같은 상한을 MCP 쪽에서도 세야 함 |
| 팀이 고치기 쉬운가 | 1차 파이프라인 코드 재사용 | 새 규격 학습 |

- 초기 의견: 1차 파이프라인(②③④)이 이미 함수로 있어 **A가 맞을 가능성이 크다.** MCP는 (ㄱ) 공공데이터 쪽이 MCP 서버를 제공하거나 (ㄴ) 개발 도구(Claude Code)에서 DB·로그를 읽는 용도가 생길 때 다시 본다.
- #224 본문의 "네이버 검색"은 결정 B(2026-11-03)로 OpenAI 웹 검색이다. 이슈 본문을 고친다.

## 9. 2026-11-05 저녁 변경 — 후보 찾기를 1차로 (PM "반영")

**🎯 바뀌는 것** — 지금은 목록에 팀이 손으로 정리한 18곳만 뜬다. 끝나면 담당자가 추천 목록에서 공정·지역·산업을 고르고 [새 후보 가져오기]를 누르면, AI가 공공자료에서 맞는 회사를 골라 목록에 더한다. 예: "전기아연도금 · 천안 · 자동차 부품" → "새 후보 12곳 들어옴 · 조사 3/12".
**🔁 흐름** — 조건 고르기 → 공장현황 파일에서 주소로 지역 추림 → AI가 생산품 글을 읽고 맞는 회사 고름(제조업이 아닌 곳은 뺌) → 고른 회사만 공장등록 조회로 업종·홈페이지·회사 전화 채움 → 목록에 더함 → 기존 자동 조사 → AI가 점수 입력 제안 → 흐린 점수로 순위에 듦 → 담당자가 확인하면 확정.
**💡 이유** — PM 정정(2026-11-05): 18곳은 팀이 찾아 온 예시이고 거산은 "이런 식이면 충분하다"고 한 것이다. 프로그램이 할 일은 조건에 맞는 후보를 찾아 주는 것이라 2차로 미룰 수 없다.
**🚫 안 고른 방법** — 산업단지 이름 조회로 목록 뽑기(1·2장의 설계) → 사례 파일 18곳 중 5곳만 나와서 버림. 산업단지 밖 공장이 많기 때문이다.
**📌 남은 것** — 대표자 이름이 필요한지 거산 확인(#275). 서버에 파일을 올리는 방법은 배포 작업(#213)에서 정함.
