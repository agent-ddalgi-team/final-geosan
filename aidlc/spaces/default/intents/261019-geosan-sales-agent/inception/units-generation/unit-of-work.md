# 작업 단위 (Units of Work) — 거산케미칼 AI 영업지원 에이전트 2차

도메인 설계의 부품 15개(`../domain-design/components.md`)를 구현 단계에서 한 번에 만들 작업 단위 11개로 묶었습니다. 기준은 `units-generation-questions.md`의 확인된 답변(Q1~Q4, 확인 후 추가 ①~④)입니다: 가치 흐름(백로그 묶음) 기준 중간 크기, 첫 단위는 걷는 뼈대(A정밀 1건 끝까지), 배포는 한 덩어리, 뼈대 뒤 독립 단위는 최대 2개 동시 진행. 어떤 순서로 만들지(경제적 순서)는 다음 단계(전달 계획)가 이 문서와 `unit-of-work-dependency.md`를 받아 정합니다. 이 문서는 순서를 추천하지 않습니다.

## 2. 단위별 책임·경계·구현 메모

### U1 `u1-skeleton` — 뼈대 (service, L)

**책임**: 팀 실천 방식의 걷는 뼈대. 가상 사례 1건(A정밀)이 파일 투입 → 필수조건 필터 → 점수 → 분류 → 추천 목록·근거 상세 화면 → 담당자 의견 저장까지 한 번에 이어지는 최소 동작. 검증 명령이 "E 77 / P 95 / S 81.1 / R 82, 필터 통과, 핵심 근거 충족, 시점 우선 접촉 후보"를 확인하고 화면에서 의견이 저장된다.

**포함 부품(최소형)**: ConfigRegistry(규칙 설정 파일 읽기·버전/해시, 담당자 목록, 거산 값 묶음 '가상 검수'), CapabilityCatalog(파일 투입·검수 상태 조회), OpportunityRegistry(가상 사례 파일 투입: 고객·기회·요구·신호·이력·발견 경로·공정 연결), RuleEngine(신규 기회 프로필 8항목, 요구 판정, 필터 상태, 핵심 근거, 시점 우선 세 요건, 운영 전제, 11분기, 정렬, 질문 후보), EvidenceExtraction(최소형: Evidence 엔티티·가상 사례 파일의 근거 자료 투입·스냅샷용 읽기 함수·상세 화면 근거 목록 조회. 홈페이지 읽기·LLM 어댑터·추출은 없음), EvaluationLedger(⓪ 평가 실행 흐름: 스냅샷·묶음·평가·항목/요구 판정·근거 연결(JudgmentEvidence)·공정 연결 현재 결과 갱신; ReadinessCheck는 가상 사례 파일 값으로 저장만), RuleEngine 입력에 조사 요건 다섯 가지(FR4.9, 가상 사례 파일 값)를 포함해 ⑧ 추가조사 / ⑨ 조건부 대기 분기까지 계산, WorkflowRunner(⓪만), ConfirmationDesk(질문 후보 저장과 조사 요건 입력값(ResearchTask) 파일 투입 저장만; 화면은 S2 상단 "확인 질문 3개 + 펼치기" 읽기 전용 영역까지), SalesRecords(의견 저장·조회만), OperatorCommands(파일 투입·평가 실행·기대값 검증 명령), WebApi(목록·상세·의견, 담당자명), WebUI(S1 신규 기회 탭·S2 신규용 상세(근거 자료 목록·확인 질문 읽기 전용 포함)·S3 의견 영역의 P0 부분, 공통 틀, 가상 데이터·내부용 띠, 쉬운 말 대응표, 테마 토큰).

**경계(뼈대에 넣지 않음)**: 외부 LLM 호출·홈페이지 읽기·근거 추출(근거 자료 자체는 파일로 투입·저장·조회한다), 전송 보호(외부로 나가는 것이 없음), 외부 소스 수집, 담기·승인·결과·활동 이력·진행 단계, 화면 기한 체크(③ 흐름), 질문 상태·요청·회신·내보내기(S6), 대시보드, 재접촉, 접속 보호, 읽기 예시 2 외 시나리오.

**구현 메모**: 시점 우선 요건 ③(담당자 체크)은 요구사항 FR10.1대로 가상 사례 파일의 "담당자 확인 체크됨" 값을 ReadinessCheck 행으로 넣어 규칙 엔진에 넘긴다(화면 체크 기능은 U5). 투입 시점에는 평가가 없으므로 ReadinessCheck.evalIdAtCheck는 비어 있음을 허용하고 첫 평가가 채우는지, 아니면 파일 값은 별도 "사전 체크" 표시로 두는지는 기능 설계로 넘기는 질문이다. 시나리오 테스트 S01~S14 중 S01·S02·S04·S06·S07·S08·S10(의견 부분)과 읽기 예시 2를 먼저 Given/When/Then으로 쓰고 통과시킨다. 교차 참조 존재 확인은 투입 순서(Customer → Opportunity → 거산 값 → 근거 → 요구·신호 → 조사 요건 → 평가)로 한다(ADR-011). 한 덩어리 실행(FastAPI가 React 빌드 결과를 내보냄)을 이 단위에서 처음 만든다.

**확장 지점을 미리 나누는 규칙(뒤 단위의 동시 진행 충돌 방지)**: WorkflowRunner는 흐름 하나 = 파일 하나(⓪ `flow_evaluate`, ① `flow_extract`, …)로 두고 흐름 표만 한 곳에 모은다. WebApi는 경로 묶음(기회 조회 / 근거 / 기록 / 질문 / 대시보드 / 접속)을 파일별로 나누고 공통 틀(접속 보호·담당자명·오류 번역)만 한 파일에 둔다. WebUI S2 근거 상세는 영역별 부품(진행 단계 / 추천 이유·확인 질문 / 요구 판정 표 / 공정 연결 / 근거 자료·주소 입력 / 점수 세부 / 기록 영역 / 활동 이력)으로 나눠 뒤 단위가 자기 영역 파일만 고치게 한다. 설정 파일 키와 쉬운 말 대응표는 뒤 단위가 "추가만" 하고 기존 키를 바꾸지 않는다.

### U2 `u2-evidence-extraction` — 근거 추출·전송 보호 (service, M)

**책임**: 홈페이지 주소 확정·본문 붙여넣기 → robots·약관 확인 → TransferGuard 등급 검사·연락처 제거 → LLM 어댑터(외부 LLM / 호출 없음) → 근거 자료·확인 질문 후보·요구 후보 저장 → ① 흐름으로 재평가 → "재평가됨"·"이전 평가 보기". 전송 로그(본문 없음)와 "전송 0건"·"거부 로그" 테스트, 월 호출 상한.

**포함 부품**: EvidenceExtraction 확장(U1의 Evidence 최소형에 홈페이지 읽기·robots 확인·LLM 어댑터(외부 LLM / 호출 없음)·추출·요구 후보·제안값/확정값 관리를 더함; 자동 탐색 제외), TransferGuard 전체(종류 태그·등급 검사·연락처 제거·전송 로그·호출/토큰 집계), WorkflowRunner ①, EvaluationLedger 재평가·이전 평가 쌍·스냅샷 등급 거르기, WebApi·WebUI의 홈페이지 주소 입력란·붙여넣기·재평가됨 띠·LLM 제안 태그.

**구현 메모**: 외부 LLM·HTTP는 테스트에서 가짜 응답으로 대체(팀 실천 방식). LLM 호출 세 지점 중 ①②만 여기서, ③ 문안 초안은 U6. S03·S11(재평가 보존) 시나리오.

### U3 `u3-source-ingestion` — 후보 수집·병합 (service, M)

**책임**: 산단공 전국등록공장현황 CSV를 설정 범위(충남+대전·세종, 생산품 키워드, 30~50건)로 읽어 후보 기업·기회·발견 경로 등록, 정규화·사업자번호/상호명+주소 병합, "확인 필요" 후보와 병합 확정 명령(⑤ 흐름), 수집 집계(IngestionRun), 소스 계약표, ⑥ 흐름.

**포함 부품**: SourceIngestion(CSV 어댑터만), OpportunityRegistry 병합·MergeCandidate, WorkflowRunner ⑤·⑥, OperatorCommands 수집·병합 확정 명령.

**구현 메모**: 인코딩(UTF-8/CP949)·헤더 검증·건너뛴 행 집계. 소스 계약표(이용·저장 허용 범위) 기록 뒤에만 실제 수집. 11/6까지 끝나야 한다(전달 계획 조건). S02 시나리오.

### U4 `u4-confirmation-desk` — 거산 확인 창구 (service, M)

**책임**: 확인 질문 상태(대기 → 요청 → 회신 → 반영 파생), 질문-기회 연결, [거산 확인 요청]·[+ 질문 직접 추가]·[회신 기록] 인라인, 질문 목록 복사·텍스트 내보내기(TransferGuard 출력 검사), S6 화면, 검수 상태 전환 명령과 ② 흐름(묶음 전체 재평가), 거산 값 묶음 전환(가상 검수 / 소개서 / 거산 확인 완료)과 "거산 확인 전" 띠·승인 비활성, 추가조사 기록(P2).

**포함 부품**: ConfirmationDesk 확장(U1의 질문 후보·조사 요건 저장에 상태 전이·연결·요청·회신·복사/내보내기를 더함), CapabilityCatalog 검수 상태 전환, WorkflowRunner ②, OperatorCommands 검수 전환 명령, WebApi·WebUI S6·S2 확인 질문 영역의 [거산 확인 요청]·[+ 질문 직접 추가] 버튼·띠.

**구현 메모**: 화면에서 거산 값을 바꾸는 경로는 없다(ADR-003). 질문 목록 복사·내보내기가 TransferGuard 출력 검사를 거치므로 U2 뒤다. S11·S12·S13·S14 시나리오.

### U5 `u5-sales-records` — 담당자 기록 (service, M)

**책임**: 담기, 접촉 승인(미정/승인/거절/취소, 목적 4개, 승인 가능 조건, 소개서 묶음 불가), 영업 결과(샘플·등록 승인 받음 포함)·접촉 시도·회신·다음 일정, 동시 수정 알림, 활동 이력, 진행 단계 Steps·배지, "이전 승인은 이전 평가 기준", 화면 기한 체크와 ③ 흐름(초기화 규칙 포함), 순위 조정 이력, 제외 기회의 재검토 조건·예정일.

**(갱신 2026-11-03, PM 결정 1·Q1~Q5) 최소형 책임 재정의 — P0, 가장 먼저**: 기획 변경 메모 4장의 네 기록 ① 접촉 시도(날짜·방법 전화/메일/방문·결과 연결됨/부재/거절) ② 영업 메모(200자 안팎, 담당자·시각 자동, 연락처 패턴이면 저장 거부, 덧붙이기만) ③ 영업 단계(미접촉 → **관심** → 접촉 → 견적·샘플 → 성사/보류/거절, 카드 꼬리표) ④ 다음 일정(날짜 + 할 일 한 줄). **담기는 만들지 않고** "관심" 단계가 대신한다(Q2). **접촉 승인은 설정 `records.approvalEnabled: false`로 화면에서 숨기고** 경로·테이블은 남긴다(Q1). 기록은 담당자 전원이 보고(Q4) 지우기 없음·단계와 일정은 새 행(Q5). 담당: 서버 이강욱(`geosan/records/`·`api/routes/records.py`), 화면 고선주, 코드표·쉬운 말 유동렬. 진행 단계 Steps·순위 조정·재검토 조건은 뒤로(B11).

**포함 부품**: SalesRecords 전체, EvaluationLedger ReadinessCheck·RankAdjustment, WorkflowRunner ③, OpportunityRegistry 재검토 조건, WebApi·WebUI S3 전체·S2 하단·진행 단계·활동 이력.

**구현 메모**: 다섯 기록은 각각 다른 테이블(FR7.1). S10 시나리오. U1의 의견 저장 코드를 확장한다.
