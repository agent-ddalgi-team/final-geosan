# 안정성 요구 (Reliability Requirements) — U1 뼈대 (u1-skeleton)

요구사항 NFR1(결정성·재현성)·NFR7(운영·복구)·NFR9(테스트·품질)·NFR12(시간 처리)를 뼈대 단위에 맞게 세분한 것입니다. 뼈대는 팀 노트북에서 돌므로 가용성 목표(SLO)는 두지 않고, "같은 입력이면 같은 결과", "실패하면 반쯤 저장된 상태가 남지 않음", "되돌릴 수 있음"에 집중합니다.

## 1. 결정성·재현성 (NFR1)

| ID | 요구 | 확인 방법 |
|---|---|---|
| NFR1.1 | 같은 확정 입력·기준일·규칙 버전·검수 값이면 규칙 엔진 결과(E/F/T/P/R/S/C, 분류, 순위)가 100% 같다(BR4.8) | 같은 입력 2회 실행 비교 테스트(AC5.1.2) |
| NFR1.2 | 규칙 엔진은 현재 시각·난수·외부 조회를 쓰지 않는다. 기준일은 입력이다 | 코드 검토 + 기준일만 바꿔 재실행 테스트 |
| NFR1.3 | 규칙 설정 파일은 버전·해시로 고정되고, 해시가 다르면 새 버전으로만 등록된다(BR7.6). 평가 묶음은 어느 버전으로 계산했는지 기록한다 | 파일 한 글자 변경 뒤 evaluate가 새 버전을 요구하는지 |
| NFR1.4 | A정밀 기대값(E 77 / P 95 / S 81.1 / R 82, 필터 통과, 핵심 근거 충족, 시점 우선 접촉 후보)과 읽기 예시 2(E 25 / P 25 / S 100 / C 12.5)는 구현 검증 명령과 시나리오 테스트의 고정 기대값이다(BR4.7) | `verify-case`, 시나리오 테스트 |
| NFR1.5 | 반올림은 HALF_UP(0.5 올림)으로 고정하고 짝수 반올림을 쓰지 않는다. 81.05 → 81.1 | 단위 테스트 |

## 2. 실패 처리·복구 (NFR7, NFR10)

| ID | 요구 | 확인 방법 |
|---|---|---|
| NFR7.1 | 한 흐름(투입 1파일, 평가 1묶음, 의견 1건)은 한 트랜잭션이며, 중간 실패 시 그 흐름의 저장을 전부 되돌리고 사유를 호출자에게 돌려준다(BR7.5). 반쯤 저장된 평가·투입이 남지 않는다 | 저장 단계에 고의 오류를 넣는 테스트 |
| NFR7.2 | SQLite 쓰기 잠금 대기는 5초, 넘으면 실패·되돌림·500(또는 종료 코드 2) | 두 쓰기를 동시에 거는 테스트 |
| NFR7.3 | 서버가 죽거나 명령이 중단돼도 데이터베이스 파일은 일관된 상태다(WAL·트랜잭션). 재시작은 1분 이내 | 평가 중 프로세스 강제 종료 뒤 재시작·조회 |
| NFR7.4 | 되돌리기 수단: 뼈대 기간에는 데이터베이스 파일 복사가 백업이다(명령은 U8 `backup`/`restore`). 투입·평가 전 파일 복사 절차를 팀원 시작 안내서에 한 줄로 둔다 | 안내서 확인 |
| NFR7.5 | 재투입은 안전하다: 같은 파일을 두 번 넣어도 결과가 같고(멱등), 검수 완료 값이 되돌아가지 않으며(BR1.7), 이전 평가가 남는다 | 같은 파일 2회 투입 테스트 |
| NFR7.6 | 마이그레이션은 되돌리기(downgrade)를 가진다(Alembic, Q2). 접두사별 파일, 머리가 둘이면 `db merge-heads` | `init-db` 2회 실행 안전, downgrade 1단계 테스트 |
| NFR7.7 | 어떤 실패도 조용히 지나가지 않는다: 명령은 종료 코드(0/1/2)와 한국어 사유, API는 오류 형식(message·nextAction·ref), 서버 로그에 ref(NFR10) | 오류 경로 테스트 2개 이상(구현 단계 지침) |

가용성(SLO)은 뼈대에서 정하지 않는다. 호스팅 환경 SLO·헬스 체크는 U8·관측 설계에서.

## 3. 시간 처리 (NFR12)

| ID | 요구 |
|---|---|
| NFR12.1 | 모든 시각은 시간대와 함께 저장하고(ISO 8601 + 오프셋), 화면은 한국 시각(Asia/Seoul)으로 보인다 |
| NFR12.2 | 감쇠·기한 계산의 기준일은 평가 묶음의 baseDate이며 수집일·투입일로 대신하지 않는다(BR2.8, BR4.4) |
| NFR12.3 | 날짜 경계는 포함 규칙을 고정한다: 공고 마감일 = 기준일 → 마감 전, 자격 validTo = 기준일 → 유효, 0~30일은 0과 30 포함 |
| NFR12.4 | 테스트는 기준일을 고정해 돌린다(오늘 날짜에 의존하는 테스트 금지) |

## 4. 테스트·품질 (NFR9)

| ID | 요구 |
|---|---|
| NFR9.1 | 줄 커버리지 80% 이상(파이썬·타입스크립트 각각), 통과를 위해 낮추지 않는다 |
| NFR9.2 | 시나리오 테스트(Given/When/Then, pytest-bdd .feature)를 먼저 쓰고 통과시킨다: 뼈대는 S01·S02·S04·S06·S07·S08·S10(의견)·읽기 예시 2. 모듈 담당이 자기 모듈 시나리오를 쓴다 |
| NFR9.3 | 규칙 계산 테스트는 A정밀·읽기 예시 2 기대값을 고정값으로 쓴다 |
| NFR9.4 | 테스트는 문서화된 준비(의존성 설치) 외 수동 설정 없이 돈다. 임시 DB 파일을 쓰고 끝나면 지운다 |
| NFR9.5 | 외부 호출은 뼈대에 없고, 있더라도 테스트에서 가짜 응답으로 대체한다(팀 실천 방식) |
| NFR9.6 | `main`에 합치기 전 CI에서 Ruff·Prettier·ESLint·테스트를 돌리고 실패하면 합치지 않는다(CI 자체는 3.7 ci-pipeline 단계에서 만들고, 뼈대 기간에는 로컬에서 같은 명령을 돌린다) |
| NFR9.7 | 구현 검증 명령 `python -m pytest -q && python -m geosan verify-case examples/case-apjeong.json`이 뼈대 체크포인트의 기준이다. 화면 빌드·코드 모양 검사가 생기면 PM에게 알리고 새로 승인받아 추가한다(전달 계획 6장) |

## 상류 문서와의 연결

- 요구사항 NFR1·NFR7·NFR9·NFR10·NFR12, 팀 실천 방식(Testing Posture custom, 커버리지 80%, 되돌리기), 구현 단계 지침(오류 처리·테스트 표준).
- 기능 명세 W3 10단계(실패 시 되돌림), 3-2 상태 기계, 7장 모서리 조건.
- 규칙 BR1.7·BR2.8·BR4.4·BR4.6~4.8·BR7.5·BR7.6·BR11.2.
- 계약 3장(재시도 없음·되돌림·잠금 5초), C6(WAL·busy_timeout 5000ms), C8(종료 코드).
