# 규모 요구 (Scalability Requirements) — U1 뼈대 (u1-skeleton)

요구사항 NFR3(동시 사용·규모)을 뼈대 단위에 맞게 세분한 것입니다. 이 시스템은 의도적으로 작습니다(단일 애플리케이션·SQLite 한 파일, 제약 CON-02). "늘리는 설계"가 아니라 "상한을 정하고 그 안에서 확실히 도는 설계"가 목표입니다.

## 1. 규모 상한 (NFR3)

| ID | 항목 | 상한 | 뼈대·부분 시연 실제 |
|---|---|---|---|
| NFR3.1 | 동시 사용자 | 5명 | 1~4명(팀), 시연 1명 |
| NFR3.2 | 후보 기업 | 1,000건 | 10~20곳 + 가상 |
| NFR3.3 | 영업기회 | 2,000건 | 10~30건 |
| NFR3.4 | 평가 기록(EvaluationRun) | 10,000건 | 수십 건(전체 평가 반복 포함) |
| NFR3.5 | 항목 판정(ItemJudgment) | 80,000행(평가 × 8) | 수백 |
| NFR3.6 | 근거 자료 | 기회당 50건, 전체 20,000건 | 기회당 2~5건 |
| NFR3.7 | 사례 파일 1개 크기 | 256KB | 수 KB |
| NFR3.8 | 데이터베이스 파일 | 500MB 이하 | 수 MB |

상한을 넘는 규모는 이번 범위 밖이며(NFR3), 넘을 조짐이 보이면 11/13 중간 점검에서 다룬다.

## 2. 설계 제약 (규모 안에서 성능 목표를 지키기 위한 것)

- NFR3.9: 단일 프로세스·단일 SQLite 파일, WAL 모드. 여러 프로세스·여러 서버·메시지 큐 없음(CON-02).
- NFR3.10: 목록 조회는 쪽 단위(20건, 최대 50건)로만 읽고 전체를 메모리에 올리지 않는다. 목록 정렬은 저장된 originalRank를 쓴다(조회 시 재정렬 없음).
- NFR3.11: 전체 평가(FULL)는 기회 수에 비례(선형)하며 기회당 1초 이내(NFR2.3). 2,000건 10분(NFR2.5)을 지키려면 기회당 평균 300ms 이하를 목표로 한다.
- NFR3.12: 평가 스냅샷(JSON)은 기회당 64KB 이하. 근거 원문은 인용 문장만 넣고 전체 본문은 넣지 않는다.
- NFR3.13: 색인: 기회별 최신 확정 평가 조회(oppId, runStatus, createdAt), 묶음별 순위(batchId, originalRank), 의견 최신 버전(oppId, version), 거산 값 묶음 조회(datasetKind, code)에 색인을 둔다(코드 생성에서 확정).
- NFR3.14: 파일 투입은 한 파일 = 한 트랜잭션. 20개 파일을 연속 투입해도 서로 막지 않는다.

## 3. 성장 시나리오 (범위 밖이지만 적어 두는 것)

| 상황 | 무엇이 먼저 막히는가 | 그때 할 일(범위 밖) |
|---|---|---|
| 기회 2,000건 초과 | 전체 평가 시간(NFR2.5), 목록 쪽 넘김 | 영향 기회만 재평가(ID 기반 찾기, 도메인 설계 EvaluationLedger 개선 항목) |
| 동시 사용 5명 초과 | SQLite 쓰기 잠금 대기 | 쓰기 경로 줄이기, 단일 쓰기 큐 |
| 평가 기록 1만 건 초과 | DB 크기·조회 | 오래된 SUPERSEDED 평가 보관 분리 |

## 상류 문서와의 연결

- 요구사항 NFR3(5명·1,000·2,000·1만), 가정 A7, 제약 CON-02.
- 계약 C1(쪽당 20건·최대 50), C6(WAL·busy_timeout).
- 기능 명세 W3·W5, 성능 요구 NFR2.3~2.5.
