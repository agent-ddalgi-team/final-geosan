# 기능 설계 질문 — U1 뼈대 (u1-skeleton)

뼈대 단위의 기능 설계(데이터 모양·업무 규칙·흐름)는 요구사항(FR1~FR14, 부록 A), 부품 목록, 계약 요약(C0~C9), 사용자 스토리로 거의 정해져 있습니다. 여기서는 앞 단계가 "기능 설계에서 정한다"고 넘긴 것과 문서끼리 어긋나 설계가 갈리는 것만 묻습니다. 화면 배치·문구·부품 이름 같은 작은 세부는 추천안으로 정하고 산출물에 기록만 합니다.

## Q1. 가상 사례 파일로 넣은 "기한 내 대응 가능" 체크는 어느 평가에 묶입니까?

시점 우선 요건 ③ "기한 내 대응 가능" 체크(FR4.7)는 담당자 입력이지만 평가 입력으로 저장되며, 체크 당시 보고 있던 평가 ID(`evalIdAtCheck`)를 함께 기록합니다. 그런데 10/30 뼈대에서는 화면 체크 기능이 없어 A정밀 가상 사례 파일의 "담당자 확인 체크됨" 값으로 넣습니다. 파일을 넣는 시점에는 아직 평가가 없으므로 `evalIdAtCheck`가 비어 있습니다. 계약 설계(C3 열린 질문)와 작업 단위 나누기(U1 구현 메모)가 이 처리를 기능 설계로 넘겼습니다. 어떻게 할까요?

A. 비워 둔 채 저장하고, 그 체크를 처음 읽어 쓰는 평가가 자기 ID를 채운다. 그 뒤 재평가는 FR4.7 유지·초기화 규칙을 그대로 따른다. (추천: 파일 값과 화면 체크가 같은 행·같은 규칙을 쓰고, 뼈대 뒤 U5가 화면만 더하면 됨)
B. 파일 값은 "사전 체크"라는 별도 표시로 두고 `evalIdAtCheck`는 영원히 비워 둔다. 화면 체크(U5)만 평가 ID를 가진다.
C. 파일 투입 직후 자동으로 평가 한 번을 돌려 그 평가 ID를 채운다. (투입 뒤 평가는 명령으로 따로 한다는 계약 C7 재투입 규칙과 어긋남)

## Q2. 10/30 A정밀 시연의 근거 상세에는 어떤 확인 질문이 보여야 합니까?

확인 질문은 "거산 값이 검수 대기·미확보·재확인이거나, 요구가 미확인·단계 미확인일 때" 시스템이 만듭니다(FR11.1). A정밀 뼈대는 거산 값 묶음 '가상 검수'(모두 검수 완료)로 돌리므로 규칙대로라면 Nadcap(요구 수준 미확인) 질문 하나만 생깁니다. 그런데 스토리 AC6.2.1과 상세 화면 그림은 "인증 범위에 아노다이징 라인이 포함됩니까?"(ISO 9001이 검수 대기일 때 생기는 질문)와 "피막 두께 15μm 이상을 요구합니까?"도 보이는 것으로 적혀 있습니다. 두 문서가 어긋나서 여쭙니다.

A. 규칙대로만 보인다: 가상 검수 묶음에서는 Nadcap 질문 1개. ISO 9001·두께 질문은 소개서 묶음(검수 대기)으로 돌릴 때 생긴다. 시연 흐름 문서의 질문 3개 예시는 소개서 묶음 기준으로 고쳐 적는다. (추천: FR11.1 규칙과 FR4.13 기대값이 그대로 맞음)
B. 가상 사례 파일의 요구마다 적힌 확인 질문 문장(`requirements[].question`)도 판정과 상관없이 상세에 보인다. 시스템 생성 질문과 "파일에 적힌 질문"을 구분 표시한다.
C. A정밀 가상 사례를 두 벌(가상 검수 묶음 / 소개서 묶음) 넣어 10/30에는 둘 다 보여 준다. 기대값 E 77은 가상 검수 묶음에서만 확인한다.

## Q3. U1 뼈대의 규칙 설계는 어디까지 넣을까요?

U1은 규칙 엔진의 신규 기회 프로필 전체를 처음 만드는 단위이고, 스토리 US5.2(요구 판정)·US5.3(11분기·정렬)이 U1에 대응됩니다. 그 수용 기준에는 뼈대 시나리오(S01·S02·S04·S06·S07·S08·S10·읽기 예시 2) 밖의 것도 있습니다: 공정 연결별 제외 범위(S09), 인증 정지 시 재평가(S11), 두께 같은 기술 조건 대조(S13), 제외 기회의 재검토 조건(S14), 핵심 근거 재확인·추가조사·조건부 대기·관찰·후순위 분기. 설계를 어디까지 적을지에 따라 10/28까지의 일 양이 달라집니다.

A. 신규 프로필 규칙 전체를 이번 설계에 적는다(S09·S11·S13·S14 포함). 코드 생성은 뼈대 시나리오 테스트를 먼저 통과시키고 나머지 시나리오 테스트는 같은 U1 안에서 뒤에 통과시킨다. (추천: 규칙 엔진은 순수 계산이라 한 번에 설계하는 편이 뒤 단위 충돌이 적음)
B. 뼈대 시나리오에 필요한 규칙만 적고, S09·S11·S13·S14 규칙은 추적표에 "뒤로 미룸"으로 표시해 뼈대 체크포인트 뒤 U1 2차 묶음에서 설계·구현한다.
C. 규칙 설계는 전체를 적되(A), S13 기술 조건 대조(숫자 사양 비교)만은 거산 사양 검수 전이라 뒤로 미룬다.

## Q4. 가상 사례 파일에 평가 기준일(`baseDate`)을 넣을까요? (약속 파일 변경)

시점 항목의 감쇠는 "평가 묶음의 기준일" 기준으로 계산합니다(FR4.3, NFR12). A정밀 기대값(증설 신호 0~30일 → 1.0, 공고 마감 전)은 기준일이 정해져야 재현됩니다. 평가 명령에는 `--base-date` 인자가 있지만(C8), 검증 명령 `geosan verify-case`가 파일만 받으면 기준일을 알 수 없습니다. 계약 C7의 가상 사례 파일 형식에는 기준일 키가 없어, 더하려면 약속 파일에 먼저 적어야 합니다.

A. 가상 사례 파일에 `baseDate` 키를 더하고(약속 파일 C7·`case-file.schema.json`에 먼저 반영, PR 체크리스트 표시), `verify-case`는 그 날짜로 평가한다. 파일에 없으면 오늘 날짜. (추천: 기대값이 파일 하나로 재현되고, S01~S14 시나리오 파일도 같은 방식을 씀)
B. 파일은 그대로 두고 `verify-case`에도 `--base-date` 인자를 둔다. 검증 명령(승인된 것)에 날짜 인자를 붙여 새로 승인받는다.
C. 가상 사례의 날짜를 모두 "기준일로부터 며칠"(상대 날짜)로 적고 평가 시점에 절대 날짜로 바꾼다. (파일 형식이 크게 바뀜)

## Q5. 소개서 묶음(거산 확인 전)으로 평가한 카드에 참고 점수를 보일까요? (10월 말 부분 시연, 2026-10-21 추가)

10월 말 부분 시연은 실제 기업 10~20곳을 소개서 묶음(검수 대기 값)으로 평가해 참고 순위·근거를 보여 주는 것입니다. 현재 화면 설계(상세 화면 3-1)는 분류가 "기다리는 중"·"준비 중"이면 카드의 점수 자리에 "--"만 보이고 참고 점수는 상세의 "점수 자세히 보기"에서만 봅니다. 그러면 목록에서 순위의 근거(점수)를 설명하기 어렵습니다.

A. 소개서 묶음에서는 카드에 "참고 81"처럼 참고 점수를 회색으로 보인다. 가상 검수·거산 확인 완료 묶음의 ②③은 지금처럼 "--". (추천: 시연 목적에 맞고 "거산 확인 전" 띠·"참고" 글자로 오해를 막음)
B. 지금 설계대로 "--"를 유지하고, 시연에서는 상세 화면의 점수 세부로 설명한다.
C. 모든 묶음에서 ②③도 참고 점수를 보인다.

## Q6. 소개서 묶음 ③준비 중 안의 순위는 무엇으로 정할까요? (가설·설정값, 2026-10-21 추가)

계약 C3는 접촉 후보가 아닌 분류(OTHER 그룹)를 "R 내림 → E → 기회 ID"로 정렬합니다. 실제 기업은 모르는 항목이 많아 R(조사 시 상한)이 모두 높아져 순위가 거의 같아집니다. 이 정렬은 기획서 부록 F.10(접촉 분류 3가지의 순서)에 없는, 팀이 화면용으로 더한 규칙이라 바꿔도 기획서 규칙·A정밀 기대값(E 77 / P 95 / S 81.1 / R 82)은 바뀌지 않습니다. 새 규칙은 '가설·설정값'(규칙 설정 파일 키 `otherGroupSort`)으로 표시합니다.

A. 소개서 묶음일 때만 OTHER 그룹을 "E 내림 → R 내림 → 기회 ID"(참고 점수 순)로 정렬한다. (추천: 부분 시연에서 "확보된 근거가 많은 순"으로 설명 가능)
B. 모든 묶음에서 OTHER 그룹을 E 순으로 바꾼다.
