# 보안 설계 (Security Design) — U1 뼈대 (u1-skeleton)

보안 요구(`../nfr-requirements/security-requirements.md` NFR4.x·NFR5.x)를 어디서 어떻게 막을지의 설계입니다. 뼈대의 보안은 "들어오는 것을 경계에서 거르고, 나가는 것이 없고, 비밀이 코드에 없다"는 세 겹이며, 인증·세션·전송 암호화는 U8, 외부 전송 보호는 U2에서 더해집니다.

## 1. 겹겹이 막기 (defense in depth, 뼈대 범위)

| 겹 | 어디 | 무엇을 막나 | 설계 |
|---|---|---|---|
| 1. 파일 경계 | `check-case`·`import-*`·`check-config` 검사기 | 연락처, 모르는 키, 허용 값 밖, 범위 밖 참조, 비밀 키 | pydantic 모델 + 위치 정보 로더 + 연락처 패턴 검사기 한 곳(`geosan/config/validators` 공용 모듈). 한 항목이라도 오류면 저장 없음(NFR4.11) |
| 2. API 경계 | FastAPI 요청 모델·의존성 | 형식·길이·열거값, 담당자 키, 본문 크기, 연락처(의견 메모·사유) | 요청 모델로 검증 → 400 fields[]; 담당자 키 의존성 함수로 403; 본문 64KB 상한; 같은 연락처 검사기 재사용(NFR4.1·4.8·4.12) |
| 3. 저장 경계 | 저장소 모듈 | 다른 접두사 테이블 쓰기, 검수 완료 되돌림, 외래 참조 없는 저장 | 소유 부품의 함수로만 쓰기(접두사 규칙 C6), 재투입 규칙(BR1.7), 존재 확인(BR2.3) |
| 4. 출력 경계 | 응답 조립·로그 포매터 | FORBIDDEN 원문, 내부 오류·스택, 비밀 값 | 근거 조회 함수가 FORBIDDEN을 기본 제외; 오류 응답은 message·nextAction·ref만; 로그 포매터가 금지 필드(quote·memo·password·key)를 아예 받지 않음(NFR4.2·NFR10.3) |
| 5. 화면 | React | HTML 주입 | 기본 이스케이프, dangerouslySetInnerHTML 금지(NFR4.14) |

## 2. 담당자 키 처리 (FR14.1, NFR4.8·4.9)

- 요청 헤더 `X-Staff-Key` → 의존성 함수가 앱 설정 담당자 목록과 대조. 없음/목록 밖/`viewer` → 403 `{message: "담당자를 확인해 주세요", nextAction: "상단에서 담당자를 고르세요"}`.
- 조회 경로는 키 없이 허용(뼈대 기간 로컬). U8이 세션 의존성을 같은 자리에 앞단으로 끼운다(접속 보호 켜짐이면 세션 없을 때 401).
- 화면은 담당자 미선택·viewer면 기록 버튼 비활성 + 글자(실수 방지). 한계("인증 아님")는 띠 "내부용"과 안내서에 적는다.

## 3. 비밀·환경 (NFR4.4, NFR11.2)

- 읽는 환경 변수: `GEOSAN_DB_PATH`(기본값 `./data/geosan.db`)뿐. `GEOSAN_PASSWORD`는 U8.
- `.env.example`만 커밋, `.env`·`data/*.db`·`backups/`·`logs/`는 `.gitignore`.
- `check-config`는 설정 파일에 `password`·`apiKey`·`token` 같은 키가 있으면 오류로 막는다(NFR4.13).

## 4. 외부 호출 없음의 구조적 보장 (NFR4.3)

- U1 패키지에는 HTTP 클라이언트·LLM SDK 의존성을 넣지 않는다(`pyproject.toml` 의존성 목록으로 확인). U2가 `evidence/` 안에 어댑터를 더할 때 TransferGuard를 함께 넣는다.
- 테스트는 네트워크를 막은 상태(소켓 차단 픽스처)로 돌려 외부 호출이 생기면 실패한다.

## 5. 거산 값 묶음 분리 (NFR4.6)

- 모든 cap_ 조회 함수는 `datasetKind`를 필수 인자로 받고, 평가 스냅샷 생성은 앱 설정 `activeDatasetKind`를 넘긴다. "묶음 없이 전체 조회"하는 함수를 두지 않는다.
- 공정 연결은 `processCode`로 저장하고 평가 때 활성 묶음에서 해석하므로, 묶음을 바꿔도 기회 데이터는 그대로다.

## 6. 감사·추적 (NFR5)

- 모든 업무 테이블의 공통 열(`created_at`·`created_by`·`session_ref`)은 저장소 기본 모델이 자동으로 채운다(명령은 `system` 또는 `--by` 인자, API는 담당자 키).
- 평가·의견·검수 기록은 "새 행" 원칙이라 UPDATE가 없다(저장소 함수에 update 경로를 만들지 않음; 예외는 OppProcessLink 파생값·엔티티의 검수 상태 사본).

## 7. 위협별 대응 요약

| 위협 | 설계 대응 |
|---|---|
| 연락처 저장 | 1·2겹 검사기, DB 전체 검색 테스트 |
| 내부 자료 외부 유출 | 외부 호출 없음(4장), FORBIDDEN 출력 제외(4겹), U2 전송 보호 |
| 검수 전 값으로 통과 | 묶음 분리(5장), BR1.3·BR3.2 |
| 다른 담당자 키로 기록 | 잔여 위험으로 명시(NFR4.9), 계정은 G0 이후 |
| 파일 경로 탈출 | 명령 인자 경로를 절대 경로로 정규화하고 `..`·심볼릭 링크는 경고 후 거부(코드 생성) |
| 의존성 취약점 | 잠금 파일 + `pip-audit`·`npm audit`(CI 3.7, 뼈대 기간 수동 1회) |

## 상류 문서와의 연결

- 보안 요구 NFR4.1~4.17, NFR5.1~5.4; 기술 묶음(pydantic·FastAPI 의존성 주입·React).
- 기능 명세 W2·W7, 규칙 BR1.3·BR1.7·BR2.1~2.3·BR7.3·BR9.3·BR11.3.
- 계약 C1 보안 경계(세션 U8), C4 전송 보호(U2), C6 접두사 소유.
