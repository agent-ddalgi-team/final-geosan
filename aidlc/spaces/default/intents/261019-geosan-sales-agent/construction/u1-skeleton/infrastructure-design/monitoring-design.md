# 모니터링 설계 (Monitoring Design) — U1 뼈대 (u1-skeleton)

관측 설계(`../nfr-design/observability-design.md`)를 로컬 실행 환경에 맞춘 것입니다. 모니터링 서비스·대시보드·알림은 없고, **로그 파일과 기록 테이블을 사람이 본다**가 전부입니다. 호스팅 뒤의 헬스 체크·알림은 U8/11월 인프라 설계에서 더합니다.

## 1. 지표와 KPI (Metrics & KPIs)

| Metric | Source | Threshold | Why it matters |
|---|---|---|---|
| 목록·상세 요청 소요(ms, p95) | 요청 로그 `http.request`의 `ms` | 서버 1,000ms 초과 시 원인 조사(NFR2.1·2.2) | 3초 목표를 지키는지 |
| 평가 1건 소요(ms) | `cmd.evaluate.done`의 `ms ÷ count` | 1,000ms 초과(NFR2.3), 300ms 초과면 2,000건 10분 위험(NFR3.11) | 전체 평가 시간 예측 |
| 전체 평가 소요 | 같은 로그 | 50건 30초(NFR2.4) | 부분 시연 데이터 기준 |
| 오류 수 | `level=ERROR` 줄 수 | 시연 전 24시간 0건 | 조용한 실패 없음 |
| 외부 전송 수 | 전송 로그 테이블 행 수 | 0 | 뼈대에 외부 호출 없음(NFR4.3) |
| DB 파일 크기·기회 수·평가 수 | `cmd.evaluate.done` | 상한의 75%(400MB·1,500·7,500) WARNING | 규모 상한 감시(NFR3) |
| 연락처 패턴 거부 수 | 검사기 로그 `validate.contact_rejected` | 기록만 | 팀원 파일 품질 |
| 검수 상태 사본 불일치·공정 연결 재계산 | WARNING 로그 | 0건이 정상 | 데이터 일관성(NFR10.4) |

## 2. 알림 (Alerts)

| Alert | Condition | Severity | Routes to |
|---|---|---|---|
| 없음(뼈대) | — | — | 로그를 사람이 본다. 명령은 실패를 종료 코드와 한국어 사유로 바로 보인다 |
| (11월 U8) 서버 응답 없음 | 헬스 경로 실패 | P2 | 호스팅 기본 알림 → PM |

## 3. SLI / SLO

| SLI | SLO target | Measurement window |
|---|---|---|
| 없음(뼈대, 로컬 실행) | — | — |
| (11월 시연 환경부터) 헬스 경로 성공률 | 거산 사용 시간(평일 9~18시) 중 99% | 11/15~12/10 |

운영 단계(관측 설정·SLO)는 이번 범위에서 건너뛰므로, 호스팅 뒤에도 SLO는 위 한 줄 수준으로만 둔다.

## 4. 로그와 추적 (Logs & Tracing)

| 항목 | 설계 |
|---|---|
| 집계 | 없음. `logs/geosan.log`(JSON 한 줄, 일 1회 회전, 14일)와 표준 출력. 시연 뒤 로그는 저장소 밖에 두고 커밋하지 않음 |
| 조회 방법 | `jq`나 짧은 파이썬으로 `event`·`ms`·`level` 집계(코드 생성에서 `scripts/log-summary.py` 또는 안내서 예시 1개) |
| 추적 | 분산 추적 없음. 요청 ref·명령 run ID·batchId를 상관 키로 같은 로그에 붙임 |
| 대시보드 | 없음. 체크포인트 때 측정값을 `tests/perf-notes.md`에 표로 적는 것이 대시보드를 대신 |
| 기록 테이블 | "누가 언제 무엇을"은 로그가 아니라 테이블 조회로 답한다(관측 요구 NFR5.5, 조회 예시 `docs/queries.md`) |

## 상류 문서와의 연결

- 관측 설계(JSON 로그·상관 ID·지표는 로그로), 관측 요구 NFR10.1~10.13·NFR5.5, 성능 요구 측정 방법, 규모 요구 상한 감시.
- 인프라 명세 2장(로그 파일), 4장(헬스 경로는 U8).
